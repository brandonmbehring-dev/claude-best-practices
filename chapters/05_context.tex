\chapter{Context as Currency}
\label{ch:context}

\begin{itshape}
Three hours into a session, Claude starts repeating itself.
It forgets a rule you stated 20 minutes ago.
It suggests an approach you already rejected.
The code quality has noticeably dropped since the session started.
\end{itshape}

In \cref{ch:first-session}, you learned two context commands: \code{/clear}
and \code{/compact}. This chapter explains \emph{why} context degrades,
gives you a full toolkit for managing it, and introduces patterns
for cross-session persistence.

\section{Why Context Degrades}
\label{sec:context-degradation}

\marginnote[Official]{Performance degrades as context fills.
Use \code{/clear} between unrelated tasks. Use \code{/compact}
for selective summarization.\sourceurl{https://code.claude.com/docs/en/best-practices}}

\begin{whybox}[Context Rot Is Real and Measurable]\index{context!degradation}\index{context!context rot}
Anthropic calls this \textbf{context rot}: as token count grows,
accuracy and recall degrade. This is not a hard cliff but a
performance gradient---each additional token of irrelevant information
dilutes attention on the tokens that matter.\sourceurl{https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents}

The practical impact: with a full 1M window, community testing shows
quality degradation starting as early as 40\% usage, and approximately
1 in 4 retrievals failing at capacity.
The effective high-quality range is roughly 200--500K tokens---well
short of the 1M headline.

The mechanism: Claude's attention distributes across all tokens
in context. Critical instructions (your CLAUDE.md rules, the current
task description) compete for attention with accumulated noise.
Content near the beginning and end of the window is recalled more
reliably than details buried in the middle.
\end{whybox}

\section{The Full Context Toolkit}
\label{sec:context-toolkit}

\begin{description}
  \item[\code{/clear}]\index{sessions!clear@\texttt{/clear}} Wipe context and start fresh. Use between unrelated tasks.
    Cost: $\sim$30 seconds. Benefit: full attention on the next task.

  \item[\code{/compact}] Summarize conversation while preserving key decisions.\index{compaction}
    Less aggressive than \code{/clear}; retains important context.
    Use when a long task genuinely needs accumulated context but the
    window is getting large.

  \item[\code{/rewind}] Checkpoint and roll back to a previous state.
    Every action Claude takes creates an automatic checkpoint.
    Double-tap \code{Esc} or run \code{/rewind} to open the rewind menu:
    restore conversation only, restore code only, restore both,
    or summarize from a selected message.
    Checkpoints persist across sessions---you can close your terminal
    and still rewind later.

  \item[\code{/context}] Visualize current context usage.
    Shows how much of the window is consumed and by what.

  \item[\code{/btw}]\index{btw@\texttt{/btw}} Ask a side question without growing context.
    \official{The answer appears in a dismissible overlay and never enters
    conversation history.\sourceurl{https://code.claude.com/docs/en/interactive-mode}}
    Works even while Claude is processing. No tool access---answers from
    what is already in context. Zero cost to your context budget.

  \item[Subagents] Delegate context-heavy research to isolated agents.
    Results return to your session; the research context does not.
    See \cref{ch:agents} for the full treatment.
\end{description}

\margintip{\code{/btw} is the inverse of a subagent: it sees your full
conversation but has no tools. A subagent has full tools but starts
with an empty context.}

\margintip{Watch the token counter. When it approaches 60--70\% of the window,
proactively \code{/compact} or \code{/clear}.
This is a practitioner heuristic from observed quality degradation, not a hard cutoff.
Auto-compaction triggers later ($\sim$83\%) but quality has already dropped by then.}

\section{The Status Line: Zero-Cost Monitoring}
\label{sec:statusline}

\marginnote[Official]{The status line runs entirely locally---zero API tokens
consumed. Fully customizable via script.\sourceurl{https://code.claude.com/docs/en/statusline}}

\official{Claude Code displays a configurable status line showing session
metrics in real time.\sourceurl{https://code.claude.com/docs/en/statusline}}\index{status line} By default it shows the active model, git branch,
session cost, and context window usage percentage.

You can extend it with a custom script whose output is appended
to the default display:

\begin{minted}{bash}
# ~/.claude/statusline.sh — runs locally, never sent to API
#!/bin/bash
echo "env: ${APP_ENV:-dev}"
\end{minted}

The status line is your early-warning system for context degradation.
When context usage enters the 60--70\% range, proactively \code{/compact} or
\code{/clear}---do not wait for quality to degrade before acting.

\begin{tipbox}[What to Watch]
\begin{description}
  \item[Context usage \%] The single most important metric.
    Watch for the 60--70\% threshold where quality drops non-linearly.
  \item[Session cost] Tracks spend in real time. Catches expensive
    operations before they compound.
  \item[Git branch] Confirms you are working in the right context,
    especially when switching between worktrees (\cref{sec:worktrees}).
  \item[Model] Confirms which model is active---important after
    \code{--model} overrides or skill-level model switches.
\end{description}
\end{tipbox}

\practitioner{The status line costs nothing and prevents the most common
failure mode: context degradation discovered only after quality has
already dropped. Enable it on day one.}

\section{The Two-Failure Rule (Revisited)}
\label{sec:two-failure}

This rule was introduced in \cref{ch:first-session}.
Now you understand \emph{why} it works:

\practitioner{After two failed corrections, the context contains:
the original error ($\sim$500 tokens), your first correction ($\sim$200 tokens),
Claude's apology and retry ($\sim$800 tokens), your second correction ($\sim$200 tokens),
and Claude's second attempt ($\sim$800 tokens).
That is $\sim$2,500 tokens of noise---nearly all of it encoding
failure patterns rather than the actual task.}

\code{/clear} discards 2,500 tokens of noise.
A better initial prompt (informed by what went wrong)
takes $\sim$200 tokens and produces a better result.

\subsection{Customizing Compaction}

\official{You can control what survives compaction by adding instructions
to CLAUDE.md:\sourceurl{https://code.claude.com/docs/en/best-practices}}\index{compaction!CompactInstructions}

\begin{minted}{markdown}
## Compact instructions
When compacting, always preserve:
- The full list of modified files
- Any test commands and their results
- Architecture decisions from this session
\end{minted}

For targeted compaction, run \code{/compact} with a focus argument:

\begin{minted}{text}
/compact Focus on the API changes
/compact Preserve test results, discard exploration
\end{minted}

\official{Run \code{/compact <focus>} to direct summarization toward specific
context.\sourceurl{https://code.claude.com/docs/en/best-practices}}\index{compaction!compact focus@\texttt{/compact} focus}
This is strategic pre-compaction: instead of waiting for auto-compaction
to summarize \emph{everything}, you surgically remove noise while
preserving signal. Use it when switching sub-tasks within a long session.

For partial compaction, use \code{Esc + Esc} or \code{/rewind},
select a message checkpoint, and choose \textbf{Summarize from here}.
This condenses messages from that point forward while keeping
earlier context intact---more surgical than a full \code{/compact}.

\begin{warnbox}[Extended Thinking Blocks Are Compaction-Resistant]
\label{warn:thinking-compaction}
Extended thinking blocks are immutable after generation---auto-compaction
cannot summarize or truncate them. Heavy thinking sessions create
compaction-resistant context growth. Mitigations:
\begin{itemize}
  \item Use \code{/clear} after deep thinking sessions rather than compacting.
  \item Delegate thinking-heavy analysis to subagents (\cref{ch:agents})---their
    thinking context does not persist in your session.
  \item Monitor context with \code{/context} during extended thinking sessions;
    thinking tokens are billed as output tokens and consume context budget.
\end{itemize}
\end{warnbox}

\section{Strategy for 1M Context Windows}
\label{sec:1m-strategy}

\marginnote[Official]{Opus 4.6 offers a 1M-token context
window---5$\times$ the previous 200K limit. Auto-compaction
still triggers near the limit, but sessions run far longer
before it fires.\sourceurl{https://code.claude.com/docs/en/how-claude-code-works}}

\convergence{Percentage-based heuristics were calibrated for 200K windows.
At 1M, the same percentages represent vastly different absolute
quantities---and absolute noise, not the percentage, drives quality loss.}

The 1M window is a qualitative shift.\index{context!1M strategy}
With 200K tokens, aggressive context management was survival.
With 1M, you have room to breathe---but also room
to accumulate far more noise before any alarm fires.

\begin{fullwidth}
\begin{tabular}{@{}lrrp{5.5cm}@{}}
\toprule
\textbf{Metric} & \textbf{200K Window} & \textbf{1M Window} & \textbf{Implication} \\
\midrule
60\% full & 120K tokens & 600K tokens & 600K of noise is qualitatively worse \\
Auto-compaction & $\sim$166K & $\sim$830K & Sessions run $\sim$5$\times$ longer before trigger \\
Practical ceiling & $\sim$140K & $\sim$700K & Absolute token count, not \%, determines quality \\
\bottomrule
\end{tabular}
\end{fullwidth}

\subsection{PreCompact Hook for State Preservation}

\official{The \code{PreCompact} hook fires before compaction begins.
Matchers: \code{manual} (user-triggered) or \code{auto}
(system-triggered). The hook cannot block
compaction.\sourceurl{https://code.claude.com/docs/en/hooks}}\index{compaction!PreCompact hook}

Use it to serialize critical state to disk before compaction discards detail:

\begin{minted}{json}
{
  "hooks": {
    "PreCompact": [{
      "matcher": "auto",
      "hooks": [{
        "type": "command",
        "command": ".claude/hooks/pre-compact-backup.sh"
      }]
    }]
  }
}
\end{minted}

\margintip{Keep PreCompact hooks fast---they run synchronously
during compaction. A simple file copy or log append is ideal.}

\subsection{Two-Phase Compaction}
\label{subsec:two-phase-compaction}

\official{Auto-compaction proceeds in two phases: it clears older tool
outputs first, then summarizes the conversation if
needed.\sourceurl{https://code.claude.com/docs/en/how-claude-code-works}}
\index{compaction!two-phase}\index{microcompaction|see{compaction, two-phase}}

The first phase is cheap: large tool results (file reads, command output,
search results) are replaced with compact references.
These outputs are the fastest-growing context consumers---a single
\code{Read} of a 500-line file adds $\sim$2{,}000 tokens, and a
debugging session may accumulate dozens of them.
Clearing stale tool outputs recovers substantial space without losing
any of your conversation history or decisions.

\marginnote[Official]{CLAUDE.md fully survives compaction.
After compaction, Claude re-reads CLAUDE.md from disk
and re-injects it fresh.\sourceurl{https://code.claude.com/docs/en/memory}}

Only if the first phase is insufficient does auto-compaction
proceed to the second phase: summarizing the conversation itself.
This is where instructions from early in the session can be lost.
The implication: \emph{anything you want to survive compaction
should be in CLAUDE.md, not in conversation.}

\marginnote[Official]{Keep each CLAUDE.md file under 200 lines.
Total across all CLAUDE.md files: under
500 lines.\sourceurl{https://code.claude.com/docs/en/best-practices}}

\noindent\textbf{Sizing your CLAUDE.md files.}\index{CLAUDE.md!sizing}
Anthropic recommends keeping each individual CLAUDE.md file under
200 lines, with the combined total across all five possible
files (global, project, project-local, enterprise, user) staying
below approximately 500 lines. CLAUDE.md is re-injected after every
compaction, so oversized files consume a fixed percentage of your
context budget on every cycle. If you exceed these limits, extract
domain-specific guidance into \code{.claude/rules/} files with
\code{paths:} frontmatter so they load only when relevant.

\begin{whybox}[Why Two Phases Matter]
The two-phase design means auto-compaction is less destructive than
many practitioners assume. If your session is full of tool outputs
(the common case during debugging or exploration), the first phase
alone may free 30--50\% of context without touching your conversation.
If you proactively \code{/compact} before hitting the auto-trigger,
you can often stay in phase~1 territory indefinitely.
\end{whybox}

\subsection{PostCompact Hook for State Restoration}
\label{subsec:postcompact-hook}

\official{The \code{PostCompact} hook fires after compaction completes.
Matchers: \code{manual} (user-triggered) or \code{auto}
(system-triggered). Like PreCompact, it cannot block
compaction.\sourceurl{https://code.claude.com/docs/en/hooks}}
\index{compaction!PostCompact hook}

Use it to restore state that a PreCompact hook saved, or to inject
reminders into the freshly compacted context:

\begin{minted}{json}
{
  "hooks": {
    "PostCompact": [{
      "matcher": "auto",
      "hooks": [{
        "type": "command",
        "command": ".claude/hooks/post-compact-restore.sh"
      }]
    }]
  }
}
\end{minted}

\margintip{Pair PreCompact (save) with PostCompact (restore)
for automatic state checkpointing across compaction boundaries.}

\practitioner{A common PostCompact pattern: log the compaction event
with a timestamp and trigger type (\code{manual} or \code{auto})
to a file like \code{\textasciitilde/.claude/compaction.log}.
Over time, this log reveals how often auto-compaction fires
and whether your sessions are hitting the threshold too early.}

\subsection{Decision Framework for 1M}

\begin{description}
  \item[< 30\% ($<$300K tokens)] Context healthy. Work freely.
    No compaction needed.
  \item[30--60\% (300K--600K)] Optional strategic compaction if switching
    tasks. Good time for \code{/compact <focus>} to shed completed sub-tasks.
  \item[60--80\% (600K--800K)] Proactive compaction recommended.
    Quality degradation begins in this range (\cref{sec:context-degradation}).
    Use \code{/compact} or \code{/clear} if the current task is complete.
  \item[> 80\% ($>$800K)] Auto-compaction imminent.
    Consider \code{/clear} and resuming with a fresh prompt.
    Recover context from durable artifacts (\cref{subsec:durable-artifacts}).
\end{description}

\marginnote[Cross-Ref]{Extended thinking blocks resist
compaction (p.\,\pageref{warn:thinking-compaction}).
Heavy thinking sessions may need \code{/clear}
rather than \code{/compact}.}

\practitioner{The single best habit for 1M windows: invest 60 seconds
writing durable artifacts (\code{CURRENT\_WORK.md}, plan docs, git commits)
\emph{before} compacting or clearing. Compaction supplements persistence;
it does not replace it.}

\section{Context Curation for Large Codebases}
\label{sec:context-curation}

\marginnote[Tip]{Claude does not need to see your entire codebase.
It needs to see the \emph{right} parts.
Curation is the skill.}

In a 200K-line codebase, Claude cannot read everything.
The practitioner's daily challenge is not ``how do I manage context''
but \emph{``which parts of the codebase does Claude need to see
for this specific task?''}

\subsection*{The Concentric Rings Strategy}

Start narrow and expand only when Claude needs more:

\begin{enumerate}
  \item \textbf{Ring 1: The file you are changing} ($\sim$200--2{,}000 tokens).
    Claude reads it automatically. This alone is sufficient for
    simple edits and bug fixes.

  \item \textbf{Ring 2: Direct dependencies} ($\sim$2{,}000--10{,}000 tokens).
    Use \code{@path/to/interface.ts} to show the types, contracts,
    or APIs that your file depends on. Claude needs these to make
    changes that compile and pass type checks.

  \item \textbf{Ring 3: Usage sites} ($\sim$5{,}000--20{,}000 tokens).
    When changing a function signature, Claude needs to see callers.
    ``Grep for all callers of \code{processOrder()} and show me the results''
    is more efficient than loading every file.

  \item \textbf{Ring 4: Architectural context} ($\sim$1{,}000--5{,}000 tokens).
    For design decisions, Claude needs to understand the system shape.
    A well-written CLAUDE.md section on architecture
    (``we use hexagonal architecture, ports are in \code{src/ports/}'')
    conveys this in 500 tokens instead of 50{,}000.
\end{enumerate}

\begin{keyinsight}
The most common mistake with large codebases is \emph{under-curation},
not over-curation. Practitioners load a file, ask for a change, and are
surprised when Claude breaks the interface contract it never saw.
The fix is not loading the entire codebase---it is loading Ring~2
(the direct dependencies) before asking for the change.
\end{keyinsight}

\subsection*{How to Know Claude Has Enough Context}

Three signals that Claude needs more:

\begin{itemize}
  \item \textbf{Invented names.} Claude fabricates a function or
    type that does not exist. It is guessing because it has not
    seen the real API.
  \item \textbf{Wrong patterns.} Claude uses a pattern from public
    libraries instead of your internal conventions. It has not seen
    your codebase's idioms.
  \item \textbf{Confident but wrong.} Claude produces code that
    compiles but violates a constraint (thread safety, schema version,
    backwards compatibility) it was never told about.
\end{itemize}

\noindent In each case, the fix is the same: show Claude the missing
context (\code{@file}, CLAUDE.md rule, or a brief explanation),
then retry. Do not correct the output---correct the input.

\subsection*{Practical Techniques}

\begin{description}
  \item[Start with the test.] ``Read \code{tests/test\_auth.py} and then
    modify \code{src/auth.py} to fix the failing test.'' The test file
    provides Ring~2 context naturally.
  \item[Use CLAUDE.md for architecture.] A 30-line ``Architecture''
    section in CLAUDE.md replaces thousands of tokens of code reading.
    Describe the layers, the conventions, and the non-obvious constraints.
  \item[Let Claude explore.] ``Find all files related to payment
    processing'' lets Claude use Grep/Glob efficiently. It reads what
    it needs rather than you pre-loading everything.
  \item[Use \code{--add-dir} for cross-repo context.] When your change
    spans two repositories, \code{claude --add-dir ../other-repo}
    gives Claude access without context duplication.
\end{description}

\section{The Compaction Protocol}
\label{sec:compaction-protocol}

\marginnote[Tip]{Compaction is not ``press button, hope for best.''
It is a protocol with specific inputs and verification steps.}

You are at 60\% context mid-task. Auto-compaction has not triggered
but quality is starting to slip. What exactly do you do?

\subsection*{Before Compacting}

\begin{enumerate}
  \item \textbf{Write down what matters.} In 2--3 sentences, state:
    what you are working on, what decisions were made, and what
    remains to be done. This becomes your \code{/compact} focus argument.
  \item \textbf{Commit or save.} Any code changes that are ``done enough''
    should be committed or saved to a file. Compaction cannot lose
    what is already on disk.
  \item \textbf{Check for thinking blocks.} If you used extended thinking
    heavily, those blocks resist compaction
    (p.\,\pageref{warn:thinking-compaction}).
    Consider \code{/clear} instead.
\end{enumerate}

\subsection*{The Compact Command}

\begin{minted}{text}
/compact Preserve: auth refactoring decisions, test results for
  login flow. Discard: earlier exploration of caching approaches,
  failed regex attempts.
\end{minted}

\noindent Be specific about what to keep \emph{and} what to discard.
A bare \code{/compact} with no argument lets Claude decide what is
important---which may not match your priorities.

\subsection*{After Compacting: Verification}

\begin{enumerate}
  \item \textbf{Ask a recall question.} ``What architectural decisions
    did we make about the auth flow?'' If Claude cannot answer, the
    compaction lost critical context. Inject it again from your notes
    or CLAUDE.md.
  \item \textbf{Check the token counter.} Good compaction should
    reduce context by 30--50\%. If it barely moved, most of the
    context is in compaction-resistant structures (thinking blocks,
    CLAUDE.md, system prompt). \code{/clear} may be the better option.
  \item \textbf{Resume with a reorienting prompt.} ``We are refactoring
    \code{src/auth/}. The next step is to update the session middleware.''
    This anchors Claude on the current task after the context shift.
\end{enumerate}

\begin{warnbox}[Do Not Compact and Immediately Ask a Complex Question]
Compaction resets Claude's ``working memory'' even though the summary
preserves facts. Give Claude a simple orienting task first (read a file,
confirm a decision) before asking for complex reasoning. This lets
the compacted context settle into the attention pattern.
\end{warnbox}

\section{Session Management}
\label{sec:sessions}

\marginnote[Official]{Named sessions: \code{/rename}, \code{--continue},
\code{--resume}, \code{--from-pr}.\sourceurl{https://code.claude.com/docs/en/overview}}

\official{Sessions persist across terminal restarts.\sourceurl{https://code.claude.com/docs/en/overview}} Key commands:

\begin{description}
  \item[\code{claude --continue}] Resume the most recent session.\index{sessions!resume}
  \item[\code{claude --resume}] Pick from a list of previous sessions.
  \item[\code{claude --from-pr 123}] Start a session with PR context pre-loaded.
  \item[\code{/rename "feature-auth"}] Give descriptive names for later retrieval.\index{sessions!naming}
\end{description}

\subsection{Session Navigation}

The session picker (invoked via \code{claude --resume}) supports
keyboard navigation:

\begin{fullwidth}
\begin{tabular}{@{}lp{8cm}@{}}
\toprule
\textbf{Key} & \textbf{Action} \\
\midrule
\code{$\uparrow$/$\downarrow$} & Navigate session list \\
\code{P} & Preview session content without opening \\
\code{R} & Rename session inline \\
\code{/} & Search sessions by name or content \\
\code{Enter} & Open selected session \\
\bottomrule
\end{tabular}
\end{fullwidth}

\begin{tipbox}[Session Naming Conventions]
Treat sessions like branches---one logical workstream per session.
Use descriptive names that include the task type:
\code{/rename "fix-null-handling-pipeline"},
\code{/rename "feat-recency-features"},
\code{/rename "debug-cv-leakage"}.
The \code{--from-pr} flag is especially powerful for code review:
\code{claude --from-pr 142} starts a session with the full PR diff
and metadata pre-loaded, saving manual context setup.
\end{tipbox}

\subsection{Durable Artifacts: The Primary Persistence Strategy}
\label{subsec:durable-artifacts}

\convergence{Compaction alone is insufficient for multi-session work.\sourceurl{https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents}}\index{durable artifacts}
Leave clear artifacts that survive compaction, session boundaries, and
context limits:
\begin{description}
  \item[\code{CURRENT\_WORK.md}] Goal, modified files, blockers, next step.
  \item[Plan documents] For tasks spanning multiple sessions (\cref{sec:plans}).
  \item[Git commits] Persistent, verified state. Commit early and often.
  \item[Compaction] A supplement, not the primary strategy.
\end{description}

\practitioner{Maintain a \code{CURRENT\_WORK.md} file at project root.
It provides 30-second context resume after any interruption.}

\begin{fullwidth}
\begin{beforeafter}
\before
\begin{minted}{text}
[No file. Developer spends 10 minutes re-discovering context.]
\end{minted}

\after
\begin{minted}{markdown}
## Right Now
Refactoring feature engineering to use
sklearn Pipelines.

## Why
Current feature code leaks test data during
cross-validation.

## Next Step
Write tests verifying no leakage across CV folds.

## Context When I Return
- Pipeline code in src/features/pipeline.py
- 3 of 7 transformers converted, 4 remaining
- Tests in tests/features/ — existing tests pass
\end{minted}
\end{beforeafter}
\end{fullwidth}

\margintip{Update CURRENT\_WORK.md at the start and end of every session.
60 seconds invested saves $\sim$10 minutes of re-discovery.}

\section{Auto-Memory and Cross-Session Persistence}
\label{sec:memory}

\marginnote[Official]{Claude records and recalls memories across sessions
automatically. Memory files persist in \code{\textasciitilde/.claude/projects/*/memory/}.\sourceurl{https://code.claude.com/docs/en/memory}}

\official{Claude maintains auto-memory that persists across conversations.\sourceurl{https://code.claude.com/docs/en/memory}}\index{memory!auto-memory}
It records patterns, decisions, and lessons learned, making them available
in future sessions without explicit re-prompting.

\subsection{What to Store in Memory}

\begin{description}
  \item[Stable patterns] Confirmed conventions that apply across sessions
  \item[Architecture decisions] Why you chose X over Y (not just what)
  \item[Hard-won lessons] Bugs, workarounds, gotchas that took time to discover
  \item[Known issues] Pre-existing problems to avoid re-investigating
\end{description}

\subsection{What NOT to Store}

\begin{description}
  \item[Transient state] Current task details, in-progress work
  \item[Unverified conclusions] Patterns seen once, not confirmed
  \item[Duplicates of CLAUDE.md] Memory supplements configuration, does not replace it
\end{description}

\begin{fullwidth}
\begin{beforeafter}[Memory Entries]
\before
\begin{minted}{markdown}
# Memory
The project uses pandas. We had a bug
once. Config is in settings.yaml. I like
using polars. Testing is important.
\end{minted}

\after
\begin{minted}{markdown}
# Architecture Decision
Feature pipelines use polars (not pandas)
since 2026-01. Migration complete for
src/features/. Tests still use pandas
fixtures — convert as encountered.

# Known Gotcha
scikit-learn ColumnTransformer silently
drops columns not in the transformer list.
Always verify output columns match schema
after pipeline.fit_transform().
\end{minted}
\end{beforeafter}
\end{fullwidth}

\begin{tipbox}[Memory vs.\ CLAUDE.md vs.\ CURRENT\_WORK.md]
Three persistence mechanisms, each for a different purpose:
\begin{description}
  \item[CLAUDE.md] Project rules that apply every session. Actionable instructions.
  \item[Memory] Lessons and patterns that emerged organically. Supplements CLAUDE.md.
  \item[CURRENT\_WORK.md] Transient state: what you are doing right now. Updated every session.
\end{description}
If a memory entry becomes a rule, promote it to CLAUDE.md and delete the memory.
If a memory entry becomes stale (the bug was fixed, the pattern was abandoned),
delete it---stale memories are noise.
\end{tipbox}

\practitioner{The test for whether something belongs in memory:
``Will this still be true and useful in three months?''
If yes, store it. If uncertain, wait for confirmation.}

\section{Plan Documents for Large Tasks}
\label{sec:plans}

\marginnote[Official]{Use Plan Mode (Shift+Tab) for read-only analysis
before implementation.\sourceurl{https://code.claude.com/docs/en/overview}}

\official{The recommended workflow for complex tasks:
Explore $\rightarrow$ Plan $\rightarrow$ Implement $\rightarrow$ Commit.\sourceurl{https://code.claude.com/docs/en/best-practices}}

Plan Mode lets Claude analyze your codebase without modifying anything.
Use it for architecture discussions, impact analysis, and strategy decisions.

\practitioner{For tasks exceeding one hour or 500 lines of changes,
create a plan document:}

\begin{enumerate}
  \item \textbf{Active} --- currently being planned, open questions remain
  \item \textbf{Ready} --- plan approved, implementation can begin
  \item \textbf{Implemented} --- all phases complete
  \item \textbf{Archived} --- moved to \code{docs/plans/archived/}
\end{enumerate}

Every plan document should include a ``Decisions Made'' section
documenting: why specific implementations were chosen,
alternatives considered but rejected, assumptions made,
and tradeoffs accepted. This section is invaluable for postmortem analysis
when a decision turns out to be wrong.

\marginnote[Cross-Ref]{For collaborative plan drafting and ADRs,
see \cref{ch:thinking-partner}.}

\section{Context Budget Planning}
\label{sec:context-budget}

\marginnote[Tip]{Estimate context needs
\emph{before} starting. A 5-second
estimate prevents a 10-minute recovery.}

Before starting a task, estimate whether it fits in your current
session or needs a fresh one:

\begin{fullwidth}
{\small
\begin{tabular}{@{}lrp{6cm}@{}}
\toprule
\textbf{Action} & \textbf{Tokens} & \textbf{Notes} \\
\midrule
Startup overhead & $\sim$8K & System prompt + CLAUDE.md + env + MCP \\
Reading a source file & 1,000--3,000 & Largest single consumer per action \\
Edit cycle (edit + verify) & 500--1,000 & Per file edited \\
Test suite output & $\sim$1,200 & Filter with hooks to reduce \\
Search results (grep/glob) & $\sim$600 & Per search \\
Claude's analysis & 400--800 & Per response \\
\bottomrule
\end{tabular}
}
\end{fullwidth}

\noindent\textbf{Rule of thumb}: A focused task touching 5--10 files
consumes 30--50K tokens. A broad investigation can consume 100K+ easily.
If your task will read more than 20 files, delegate research to
a subagent (\cref{ch:agents}).

\subsection*{When to Split into Multiple Sessions}

\begin{description}
  \item[Single session] Task touches $\leq$10 files, requires one
    coherent chain of reasoning, fits in 50--100K tokens.
  \item[Multiple sessions] Task has independent phases
    (architecture $\rightarrow$ implement $\rightarrow$ test $\rightarrow$
    integrate). Each phase gets a fresh session with a handoff file.
  \item[Parallel sessions] Tasks are independent (different modules,
    different repos). Use git worktrees (\cref{sec:worktrees}) for
    file isolation.
\end{description}

\section{Horizontal Scaling: Many Sessions, Not Deep Context}
\label{sec:horizontal-scaling}

\marginnote[Practitioner]{Claude Code's creator runs 10--15
simultaneous sessions. Horizontal
scaling beats deep context.}

The instinct is to keep one long session going---adding context,
compacting, adding more. But 1M tokens of deep context performs
worse than five 200K-token sessions running in parallel.

\subsection*{The Pattern}

\begin{enumerate}
  \item \textbf{One session per task.} ``Fix the auth bug'' gets its
    own session. ``Add the caching layer'' gets another. Each starts
    fresh with focused context.
  \item \textbf{Git worktrees for isolation.} \code{claude --worktree}
    gives each session its own copy of the repository. No file conflicts.
  \item \textbf{Handoff files for continuity.} When a session produces
    decisions that the next session needs, write a handoff file:
    what was decided, what was changed, what remains.
  \item \textbf{CLAUDE.md as shared memory.} All sessions read the
    same CLAUDE.md. Project conventions, architecture decisions, and
    constraints propagate automatically.
\end{enumerate}

\begin{keyinsight}
The context window is not a workspace---it is a conversation.
Conversations degrade over time. The solution is not a bigger window;
it is shorter, more focused conversations with durable artifacts
bridging between them. Think of each session as a function call:
clear inputs (CLAUDE.md + handoff file), focused execution, clear
outputs (commits + handoff for next session).
\end{keyinsight}

\subsection*{When to Go Deep vs.\ Wide}

\begin{description}
  \item[Go deep (single long session)] The task requires continuous
    reasoning across many interconnected decisions. Splitting would
    lose critical context. Examples: debugging a subtle race condition,
    designing a complex API where each endpoint depends on the others.
  \item[Go wide (multiple short sessions)] The tasks are independent
    or can be serialized with handoff files. Examples: implementing
    separate features, reviewing multiple PRs, batch operations
    across files.
\end{description}

\practitioner{Default to wide. Most work decomposes into independent
units better than practitioners expect. The overhead of a handoff
file (2 minutes to write) is almost always less than the cost of
context degradation in a 3-hour session.}

\section{Quick Reference}

\begin{itemize}
  \item Context degrades non-linearly---manage it actively
  \item \code{/clear} between tasks, \code{/compact} within long tasks
  \item \code{/context} to visualize usage, \code{/rewind} to undo missteps
  \item Two-failure rule: \code{/clear} + better prompt beats a third correction
  \item \code{/compact <focus>} for surgical pre-compaction; PreCompact hook for state backup
  \item Auto-compaction clears tool outputs first, then summarizes conversation (\cref{subsec:two-phase-compaction})
  \item Pair PreCompact + PostCompact hooks for automatic state checkpointing
  \item For 1M windows: think in absolute tokens, not percentages (\cref{sec:1m-strategy})
  \item CURRENT\_WORK.md for cross-session context at project root
  \item Auto-memory for cross-session patterns
  \item Plan Mode (Shift+Tab) before complex implementations
\end{itemize}
