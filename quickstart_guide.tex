% --- The Contract ---
By the end of this hour, you will have:
\begin{enumerate}
  \item Claude Code installed and running in your project
  \item Your first AI-assisted test (a real test in your test suite)
  \item Your first AI-assisted commit (a real commit in your history)
  \item A CLAUDE.md that encodes your project's standards
  \item A clean session close with context for next time
\end{enumerate}

\margintip{Already comfortable with Claude Code? Skip to \emph{Your First CLAUDE.md} (\cref{sec:claudemd}) --- the essential commands table is on the last page.}

\textbf{Four terms you'll encounter} (defined again in the margins on first use):
\begin{description}[leftmargin=2.2cm, style=sameline, font=\bfseries]
  \item[Session] Your conversation with Claude Code, persisted across terminal restarts.
  \item[Tool use] When Claude runs a command, reads a file, or edits code on your behalf.
  \item[CLAUDE.md] A file where you give Claude persistent instructions about your project.
  \item[Permission] Whether Claude asks before acting or acts autonomously.
\end{description}

% =====================================================================
\section{Safety}

\subsection{Install and Launch (Minutes 0--5)}

\begin{minted}{bash}
npm install -g @anthropic-ai/claude-code
cd your-project
claude
\end{minted}

\margintip{Requires Node.js 18+. If you don't have it: \code{nvm install 18}.}

\marginnote[Vocab]{\textbf{Session} --- your conversation with Claude, persisted across terminal restarts. Resume anytime with \code{claude -{}-continue}.}

% Example output (yours will differ):
\begin{minted}[frame=none]{text}
  Welcome to Claude Code!
  /help for commands, /quit to exit

>
\end{minted}

You have a prompt. Claude is ready.

\begin{tipbox}[If Something Goes Wrong]
\begin{itemize}[itemsep=1pt]
  \item \textbf{Auth error} --- Run \code{claude login} and follow the prompts.
  \item \textbf{Wrong directory} --- Claude works best in a project root with source files.
  \item \textbf{No project handy} --- Try it on any git repo, even a small one.
\end{itemize}
\end{tipbox}

% -----------------------------------------------------------------
\subsection{Your First Question (Minutes 5--10)}

Ask Claude to explain your codebase:

\begin{minted}{text}
You type: "What does this project do? Focus on the main
          entry points and data flow."
\end{minted}

\margintip{The \code{@} prefix loads file content before Claude responds --- more precise than describing what to read.}

% Example output (yours will differ):
\begin{minted}[frame=none]{text}
This project is a demand forecasting pipeline with three
main components:
  - Data ingestion: src/data/load.py
  - Feature engineering: src/features/build.py
  - Model training: src/models/train.py
The entry point is main.py, which orchestrates...
\end{minted}

Now ask something specific:

\begin{minted}{text}
You type: "@src/features/build.py explain this function's
          edge cases — what happens with empty input?"
\end{minted}

\marginnote[Cross-Ref]{For the full vocabulary of precision prompting, see Ch4.}

Claude returns a real explanation of \emph{your} code. It didn't guess --- it used tools to examine your source files. Notice: the second prompt was more specific and got a better answer. That's the specification skill.

% -----------------------------------------------------------------
\subsection{Safety Net and First Edit (Minutes 10--15)}

Before we ask Claude to change anything --- your safety nets:

\begin{keybox}[Your Safety Net]
\begin{description}[leftmargin=2.2cm, style=sameline, font=\bfseries\ttfamily, itemsep=2pt]
  \item[Esc] Stop Claude mid-action. Context preserved, nothing lost.
  \item[Esc+Esc] Open rewind menu. Restore conversation, code, or both.
  \item[Approval] Claude always asks before editing. You approve or reject every change.
\end{description}
\end{keybox}

\margintip{Nothing is permanent until you approve it. If anything goes wrong, \code{Esc + Esc} rewinds to any previous state.}

Now, your first edit:

\begin{minted}{text}
You type: "Add a one-line docstring to build_features()
          describing what it does and what it returns."
\end{minted}

\marginofficial{Five permission modes exist. \code{Shift+Tab} cycles through Normal, Auto-Accept, and Plan.\sourceurl{https://code.claude.com/docs/en/permissions}}

Claude reads the function, writes the docstring, and shows you a diff. A permission dialog appears. Read the diff --- does it match the function's actual behavior? If yes, approve.

\marginnote[Vocab]{\textbf{Tool use} --- each file read, edit, or command Claude runs is a tool call. You just saw three: read the file, write the docstring, show the diff.}

\begin{tipbox}
Notice how Claude broke this into steps: read the function, understand it, write the docstring, ask for approval. That's an \emph{agent loop} --- the same pattern you'd use when designing agents for your team.
\end{tipbox}

\begin{warnbox}[Precision Matters]
\textbf{Vague:} ``Add some documentation''\\
\hspace*{1em}$\rightarrow$ Claude guesses which functions, what style, how verbose

\textbf{Precise:} ``Add a one-line docstring to \code{build\_features()} describing what it does and what it returns''\\
\hspace*{1em}$\rightarrow$ One function, one change, verifiable result
\end{warnbox}

% --- Act 1 → Act 2 transition ---
\begin{whybox}[The Shift]
You just described what you wanted and verified the result --- without writing a line of code yourself. That's the new loop: \emph{specify} what you want, \emph{observe} what Claude produces, \emph{refine} if needed. The implementation is Claude's job. Knowing what ``correct'' looks like is yours.

Now let's make ``correct'' concrete --- with tests.
\end{whybox}

\section{Understanding}

\subsection{Explore, Then Test (Minutes 15--25)}

The core loop: explore $\rightarrow$ implement $\rightarrow$ verify.

\textbf{Step 1 --- Explore:}

\begin{minted}{text}
You type: "Explain what build_features() does, including
          edge cases. What happens with empty input?
          What about missing keys?"
\end{minted}

Claude explains the function's behavior, including cases you may not have considered.

\textbf{Step 2 --- Write a test:}

\begin{minted}{text}
You type: "Write a test for build_features() that covers:
          - Normal input with expected output
          - Empty input
          - Missing required keys
          Put it in tests/test_features.py"
\end{minted}

\marginofficial{``Give Claude a way to verify its own work'' is Anthropic's stated single highest-leverage practice.\sourceurl{https://code.claude.com/docs/en/best-practices}}

Claude writes the test file. Permission dialog appears. Approve it.

\textbf{Step 3 --- Run the test:}

\begin{minted}{text}
You type: "Run the test."
\end{minted}

% Example output (yours will differ):
\begin{minted}[frame=none]{text}
tests/test_features.py::test_normal_input PASSED
tests/test_features.py::test_empty_input PASSED
tests/test_features.py::test_missing_keys PASSED
3 passed in 0.42s
\end{minted}

Your code now has a regression test it didn't have five minutes ago. If tests \emph{fail} --- even better. Claude just found a bug. The test caught a real issue. This is exactly why we test.

\marginnote[Cross-Ref]{For the full TDD workflow and 6-layer validation architecture, see Ch6.}

\margintip{Tests constrain implementation. When Claude writes code to pass \emph{your} tests, the ``looks correct but is subtly wrong'' failure mode is caught automatically.}

\begin{whybox}[Why Testing Is the Core Skill]
AI-generated code has a specific failure mode: it \emph{looks correct}. Clean syntax, reasonable names, plausible logic. The bugs are subtle, not obvious. Your ability to define what ``correct'' means --- through tests --- is now more valuable than your ability to write the implementation.
\end{whybox}

\begin{tipbox}
You defined what ``correct'' means for this function. In agent design, these become guardrails --- the verification criteria that keep autonomous systems producing trustworthy results.
\end{tipbox}

% -----------------------------------------------------------------
\subsection{Review, Regression, and Commit (Minutes 25--35)}

\textbf{Step 1 --- Review the diff:}

\begin{minted}{text}
You type: "Show me all the changes we've made this session."
\end{minted}

\begin{tipbox}[Reading Diffs --- What to Check]
\begin{itemize}[itemsep=1pt]
  \item Does the docstring match the function's \emph{actual} behavior?
  \item Does the test import the right module?
  \item Are there any changes you didn't expect?
  \item Does the test actually assert correctness, not just ``doesn't crash''?
\end{itemize}
\end{tipbox}

\textbf{Step 2 --- Regression check:}

\begin{minted}{text}
You type: "Run the full test suite to make sure our changes
          didn't break anything."
\end{minted}

\marginnote[Vocab]{\textbf{Regression testing} --- verifying that new code doesn't break existing behavior. The practice that turns a collection of scripts into reliable software.}

This takes 30 seconds and catches the most expensive bugs --- the ones where a fix in one place breaks something elsewhere.

\textbf{Step 3 --- Commit:}

\begin{minted}{text}
You type: "Commit these changes with message:
          'Add docstring and tests for build_features'"
\end{minted}

\marginnote[Cross-Ref]{For context management during long sessions, see Ch5.}

Claude stages the files, writes the message, and commits. It used multiple tools in sequence --- diff, stage, commit --- without you specifying each step. You described the \emph{outcome}; Claude figured out the \emph{procedure}. That's the specification skill: describe what, not how.

% --- Act 2 → Act 3 transition ---
\begin{whybox}[From Builder to Architect]
You didn't write the test or the docstring --- but you defined what they should do, verified the result, and caught a real issue. Your value shifted from \emph{typing code} to \emph{defining correctness}. That's not a demotion --- it's an upgrade. Architects who can verify are more valuable than typists who can implement.

Now let's make these practices permanent.
\end{whybox}

\section{Ownership}

\subsection{Your First CLAUDE.md (Minutes 35--45)}
\label{sec:claudemd}

\begin{minted}{text}
You type: /init
\end{minted}

\marginofficial{CLAUDE.md loads automatically every session. It is the single most important configuration file.\sourceurl{https://code.claude.com/docs/en/best-practices}}

Claude generates a starter CLAUDE.md from your project structure. Review it --- it's a starting point, not finished. Let's make it yours.

\textbf{Add three things:}

\textbf{1. Build commands} --- tell Claude how to verify:

\begin{minted}{markdown}
## Build & Verify
- `pytest tests/` — run test suite
- `ruff check src/` — lint (if applicable)
\end{minted}

\textbf{2. Testing standard} --- make it non-negotiable:

\begin{minted}{markdown}
## Standards
- Write tests before implementation
- Run tests after every code change
\end{minted}

\textbf{3. Documentation standard} --- one line is enough:

\begin{minted}{markdown}
- Every public function must have a docstring
\end{minted}

\margintip{Keep CLAUDE.md under 300 lines. Move module-specific rules to \code{.claude/rules/} with path filters.}

\marginnote[Cross-Ref]{For the full CLAUDE.md architecture (rules, settings, hooks), see Ch8.}

Here's what a mature CLAUDE.md looks like after a few sessions of refinement:

\begin{minted}{markdown}
# Demand Forecasting

## Build & Verify
- `pytest tests/` — run test suite
- `mypy src/` — type checking
- `ruff check src/` — lint

## Architecture
- src/features/ — feature engineering pipelines
- src/models/ — model training and evaluation
- src/data/ — data loading and validation
- tests/ — mirrors src/ structure

## Standards
- Type hints on all function signatures
- Run tests after every code change
- Never commit without passing lint + tests
\end{minted}

\begin{warnbox}
Do NOT write: \emph{``This is an ML project. We use scikit-learn. Tests are important.''}\\
DO write: \textbf{commands}, \textbf{locations}, and \textbf{rules} --- not descriptions.
Claude needs to know how to \emph{work on} your project, not \emph{about} it.
\end{warnbox}

\begin{tipbox}
CLAUDE.md is your first agent configuration file. Every agent you build --- for your team, for a pipeline, for production --- will need something like it: persistent instructions that shape behavior without requiring human presence.
\end{tipbox}

Your standards are now infrastructure, not memory. Every future session starts from this baseline.

\subsection{Close Cleanly (Minutes 45--55)}

\textbf{Step 1 --- Name the session:}

\begin{minted}{text}
You type: /rename first-session-demand-forecast
\end{minted}

\margintip{Treat sessions like branches --- one logical workstream per session. Resume later with \code{claude -{}-continue} or \code{claude -{}-resume}.}

\textbf{Step 2 --- Check context:}

\begin{minted}{text}
You type: /context
\end{minted}

\marginwarning{When context usage crosses 60\%, quality drops non-linearly. Proactively \code{/compact} or \code{/clear}.}

\marginnote[Cross-Ref]{For the full context toolkit (status line, CURRENT\_WORK.md, auto-memory), see Ch5.}

\textbf{Step 3 --- Clear for next task:}

\begin{minted}{text}
You type: /clear
\end{minted}

Fresh context for the next task. The session is saved --- resume anytime.

\begin{keybox}[Three Rules That Prevent 90\% of Frustration]
\begin{enumerate}
  \item \textbf{One task per session.} \code{/clear} between unrelated work.
  \item \textbf{Two-failure rule.} After two failed corrections $\rightarrow$ \code{/clear} + better prompt. Don't push through noise.
  \item \textbf{Tests, not trust.} If Claude's code looks right but has no test, it's not done.
\end{enumerate}
\end{keybox}

\marginnote[Cross-Ref]{For the full anti-patterns catalog (six traps and their escapes), see Ch11.}

% --- Act 3 closing ---
\begin{whybox}[Infrastructure Not Memory]
You encoded your standards into CLAUDE.md so they persist without you remembering them. You named your session so you can find it later. You cleared context so the next task starts clean. This is the collaboration skill: designing systems that work reliably --- whether the collaborator is Claude, an agent you build, or a future teammate.
\end{whybox}

Everything you practiced today --- specification, verification, collaboration design --- is the foundation of effective AI-assisted development. The skills transfer directly to building agents, designing pipelines, and working with AI tools beyond Claude Code. The handbook's 16 chapters deepen every practice you touched in this hour.
